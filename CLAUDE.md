# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Projekt

ImageStudio: aplikacja WPF (.NET 10, `net10.0-windows`, x64) do generowania i edycji obrazów, wideo oraz czatu z modelami AI. Kod, komentarze i UI są po polsku; trzymaj ten język. Repozytorium nazywa się `uberllm-proxy` z historycznych powodów. `NOTES.md` opisuje dawne proxy Node (`proxy.mjs`), którego już nie ma w repo, więc nie traktuj go jako opisu obecnego kodu.

## Komendy

```powershell
dotnet build ImageStudio.slnx
dotnet test ImageStudio.Tests                       # xUnit, całość
dotnet test ImageStudio.Tests --filter "FullyQualifiedName~PromptEditorTests"   # jedna klasa/test
dotnet run --project ImageStudio                    # Debug otwiera też konsolę z logami (OutputType Exe)
dotnet publish ImageStudio -c Release -r win-x64 --self-contained   # wersja samodzielna
```

Przy dziwnych błędach brakujących plików `obj` (np. `BG1002`, `CS2001`) usuń katalogi `bin`/`obj` i zbuduj z `-m:1`; równoległy build kilku projektów XAML bywa wyścigiem.

Wersje pakietów są centralne (`Directory.Packages.props`), a TFM, `UseWPF`, nullable i `PlatformTarget` w `Directory.Build.props`. W csproj dodawaj `PackageReference` bez `Version`. Nie ma lintera.

## Architektura

- **Dependency injection (Microsoft.Extensions.DependencyInjection, z frameworka ASP.NET Core).** Jedyny composition root to `Composition/ServiceCollectionExtensions`: `AddImageStudioCore()` (ViewModele, zakładki jako `IMainTab`, okno główne, usługi niezależne od infrastruktury) i `AddImageStudioInfrastructure()` (magazyny plikowe `File*Store`, `WpfDialogService`, `WpfThemeService`, prawdziwy dostawca z `IProviderFactory`). Dane użytkownika są za interfejsami z `Configuration/Stores.cs` (`IUserStateStore`, `IGalleryStore`, `IPresetStore`, `ISecretStore`, `ISettingsStore`, `IWindowStateStore`); nie wołaj w ViewModelach statycznych `PresetStore`/`GalleryStore`/`SecretStore`/`AppSettings.Load` ani `ThemeService`. Wyjątki: `WindowMemory.Store` (zachowanie tworzone przez XAML, composition root podmienia właściwość) oraz wnętrze `MainViewModel`, które samo tworzy `ChatViewModel`, `ToolsViewModel` i serwer MCP (cykl przez `IAppControl`). Kontener nie jest zwalniany przy wyjściu, bo `McpToolHost` jest tylko `IAsyncDisposable`; w testach zwalniaj przez `DisposeAsync`.
- **Szkielet okna głównego:** klasyczne menu u góry (te same polecenia co przyciski) i stopka (`StatusBar`): status, aktywny dostawca oraz spinner z opisem trwającej operacji. Stopkę zasila `IActivityTracker` (`MainViewModel.Activity`). Każde wywołanie API zgłasza się samo, bo `ProviderFactory` opakowuje każdego dostawcę w `ActivityAiProvider` (dekorator); wywołania spoza dostawcy (pobranie obrazu z linku, narzędzia MCP w czacie) zgłaszają się przez `Activity.Begin("...")` w `using`. W czasie operacji okno odpowiedzi (wynik / rozmowa) ma `Opacity` 0.45. Nowe wywołania sieciowe idące poza `IAiProvider` muszą same wołać `Begin`.
- **Modele czatu jak modele obrazów:** `ChatModelInfo` niesie `OwnedBy`/`InputModalities`/`Description`, a `MainViewModel.ChatModelOptions` to te same modele jako `ModelOption` (ikony: obraz, rozumowanie, ...). Selektory czatu (`ChatViewModel.ModelOptionsView` / `SelectedModelOption`) i ulepszania (`ChatModelsView` / `SelectedEnhancerModelOption`) używają `ModelPicker` z `HasFilters`; filtry (szukaj, dostawca, obraz na wejściu, preferowane) są wspólne z modelami obrazów i leżą w `MainViewModel`, a panel czatu (DataContext = `ChatViewModel`) podaje je przez `ModelPicker.FiltersContext`. Wybór jako `string` (`Chat.SelectedModel`, `SelectedEnhancerModel`) zostaje źródłem prawdy; opcje go tylko odzwierciedlają (null z selektora po ukryciu przez filtr jest ignorowany).
Ceny modeli tekstowych to `ModelPricing` w tokenach (`Unit = TokenUnit`, `PriceNow` = wejście za 1M, `OutputPrice` = wyjście, `CachePrice` = odczyt z cache); UberLLM czyta je z `price_now` na tym samym rynku co media, OpenRouter z `pricing.prompt/completion` katalogu. Pozycja modelu w listach (`ModelItemTemplate` w `App.xaml`) ma dymek po najechaniu: nazwa, opis i koszty z `ModelOption.CostText` (cena bieżąca, katalogowa, rabat, dane rynku albo informacja o braku ceny).
- **Odpowiedzi strumieniowe w czacie:** ustawienie `AppSettings.UseStreaming` (Ustawienia → Aplikacja → "Używaj odpowiedzi strumieniowej", domyślnie włączone). `IAiProvider.ChatStreamAsync(..., onDelta)` ma domyślną implementację (jedno `ChatAsync` i jeden kawałek); trzej dostawcy nadpisują ją przez `OpenAiCompat.ChatStreamAsync` (SSE, `stream_options.include_usage`, składanie `tool_calls` po `index`, kawałki rozumowania). `ChatMessage` jest obserwowalną klasą: `ChatViewModel` dodaje pustą wiadomość asystenta od razu i dopisuje do niej kawałki (`MessageUpdated` przewija widok), a na końcu uzupełnia pełnym wynikiem (`Complete`). Strumień jest w stopce, ale nie przyciemnia okna odpowiedzi (`IActivityTracker.Begin(..., dimResponse: false)`). Uwaga praktyczna: czy tekst napływa stopniowo, zależy od dostawcy i modelu (część modeli UberLLM wysyła cały strumień naraz po zakończeniu generowania).
- **Zużycie tokenów w czacie:** `ChatReply.Usage` (`TokenUsage`: wejście, wyjście, z cache) czyta `OpenAiCompat` z `usage` w kilku formatach (`prompt_tokens_details.cached_tokens`, `prompt_cache_hit_tokens`, `cache_read_input_tokens`); trafia do `ChatMessage.Usage` i jest pokazywane pod odpowiedzią (`UsageText`). Aplikacja sama niczego nie cachuje: wysyła pełną historię, a cache działa po stronie dostawcy.
- **Rozumowanie w czacie:** `IAiProvider.ChatAsync(..., ChatOptions? options)`; `ChatOptions.Parameter` to parametr, który model deklaruje w `supported_parameters` (`ReasoningSupport.ParameterFor`: `reasoning_effort` > `reasoning` > `include_reasoning`), a `OpenAiCompat` wysyła go wg stylu i czyta `reasoning_content`/`reasoning`/`reasoning_details` do `ChatReply.Reasoning` (`ChatMessage.Reasoning`, tylko podgląd, nie wraca do API). `ChatViewModel.SupportsReasoning` pokazuje sterowanie (włącz/wyłącz, poziom low/medium/high) tylko dla takich modeli; wybór jest w `UserState`.
- **MVVM na CommunityToolkit.Mvvm.** `MainViewModel` jest `partial` i rozbity na pliki per funkcja (`.Generation`, `.Video`, `.Settings`, `.Gallery`, `.References`, `.Size`, `.AppControl`, `.Helpers`). Nowa funkcja głównego okna = nowy plik partial, nie rozrost `MainViewModel.cs`. Stan użytkownika trzyma `UserState`, a dane (ustawienia, galeria, zestawy, klucze) leżą w `AppPaths.UserDataDir`. Klucze API są szyfrowane przez `SecretStore` (DPAPI).
- **Dostawcy AI za `IAiProvider`** (`ImageStudio.Providers.Core`): UberLLM, OpenRouter i OpenAI to osobne projekty `ImageStudio.Providers.*`, a kontrakty i wspólny kod OpenAI (`OpenAiCompat`) są w `Core`. Wszystkie zachowały namespace `ImageStudio.Services`, więc XAML musi odwoływać się do nich z `;assembly=ImageStudio.Providers.Core`. DLL-e dostawców (referencje `Private="false"`) trafiają do podfolderu `providers\` (build i publish, targety w `ImageStudio.csproj`), a `App` wczytuje je przez `AssemblyLoadContext.Resolving`. Aplikacja rozmawia tylko z interfejsem. Nowy dostawca = nowy projekt + wpis w `ProviderRegistry` (+ widok ustawień w `Views/Providers`). Kontrakt zawiera też `DefaultTextModel` (stała `DefaultTextModelId` w dostawcy, widoczna w `ProviderRegistry`). Użytkownik nadpisuje go w Ustawieniach przez standardowy `ModelPicker` (`ProviderModelPrefs.DefaultTextModel`; `null` = domyślny dostawcy), a `MainViewModel` używa wartości efektywnej przy wyborze modelu ulepszania i czatu. Kontrakt ma też `ReloadAsync` (katalog dostawcy: modele obrazów, wideo, tekstu i ceny jednym wywołaniem, część nieudana = `null` + `Warnings`; domyślna implementacja składa go z getterów, dostawca z cache ją nadpisuje). Używają jej `InitializeAsync` i przycisk "Odśwież" w `ModelPicker` (`ReloadCommand`, komenda `ReloadModelsCommand`), a wybory użytkownika zostają. Zmiana dostawcy przechodzi przez `MainViewModel.SwitchProviderAsync` (zeruje filtry i wybory, potem ładuje listy od nowa). Modele z różnych źródeł trafiają do wspólnego `ModelOption`, a cena pochodzi osobno z `GetPricingAsync`.
- **Selektor modeli:** jeden komponent `Views/ModelPicker` (akordeon + lista + opcjonalny panel filtrów `ModelFilterBar`) używany w panelach Generowanie, Edycja, Wideo, Czat i Ulepszanie oraz w oknie Ustawień (domyślny model tekstowy dostawcy); przyjmuje `ModelOption` albo zwykłe nazwy. Filtry (`HasFilters`) działają na `MainViewModel` przez odziedziczony DataContext, a dotyczą tylko modeli generowania i edycji.
- **Okna dialogowe przez `IDialogService`** (interfejs i rekordy wyników w `ViewModels/`, implementacja `WpfDialogService` w `Views/`, `FakeDialogs` w `ImageStudio.Tests/Fakes.cs`). Zmieniając sygnaturę interfejsu, zaktualizuj fake'a. ViewModele nie wołają `MessageBox` (użyj `Confirm`) ani `Application.Current`; wątek UI przechwytuje `SynchronizationContext` w konstruktorze `MainViewModel`.
- **Lewy panel okna głównego = wstrzykiwane zakładki w osobnych projektach** (`IMainTab` z `ImageStudio.Shared`: `Title`, `Order`, `Content` = DataContext widoku). Każda zakładka to projekt `ImageStudio.Tabs.*` (Generate, Edit, Video, Chat) z widokiem i rekordem zakładki (`GenerateTab` itd. w swoim namespace); widoki wiążą się z `MainViewModel`/`ChatViewModel` tylko przez bindingi, więc projekty nie referują aplikacji. Wspólne kontrolki (`ModelPicker`, `ModelFilterBar`, `SizePanel`) i `ModelOption` leżą w `ImageStudio.Shared` (namespace bez zmian; w XAML trzeba `;assembly=ImageStudio.Shared`). DLL-e zakładek trafiają do podfolderu `tabs\` (jak dostawcy do `providers\`, targety w `ImageStudio.csproj`, wczytuje je `App` przez `AssemblyLoadContext.Resolving`). Zakładki są rejestrowane w kontenerze jako `IMainTab` (dodatkowa = kolejna rejestracja); `MainWindow` dostaje je w konstruktorze i tworzy po jednym widoku na zakładkę z `DataTemplate` wg typu (brak szablonu = wyjątek przy tworzeniu okna). `ActiveTab` to indeks w `Tabs`; wbudowane zajmują 0-3, a logika zależna od zakładki (`RunActiveTab`, `IsChatTab`, `TabNames`) opiera się na tych indeksach. Nowa zakładka = nowy projekt `ImageStudio.Tabs.*` (+ referencja `Private="false"` w aplikacji i w testach) + wpis `DataTemplate` w `MainWindow.xaml`.
- **Okno Ustawień = wstrzykiwane zakładki** (`ISettingsTab`: `Title`, `Order`, `Apply(SettingsResult)`). `MainViewModel.OpenSettingsAsync` podaje zakładki do `IDialogService.ShowSettings`; dziś `AppSettingsTab` (ogólne) i `ProviderSettingsTab` (dostawca). `SettingsViewModel` tylko je porządkuje i składa wynik. Nowa zakładka = ViewModel implementujący `ISettingsTab` + widok + `DataTemplate` w `SettingsWindow.xaml`; brak szablonu wykrywa `SettingsWindow.EnsureTabViews` (wyjątek przed otwarciem okna).
- **Zapamiętywanie rozmiarów** to zachowanie podpinane (`Views/WindowMemory`, dane w `windows.json` przez `WindowStateStore`): `WindowMemory.Remember` jest włączone globalnie w stylu `WindowBase` (każde okno ze stylem zapamiętuje rozmiar przy zamknięciu; okno główne też położenie i maksymalizację; okna `NoResize`/`SizeToContent` pomijają rozmiar), a `WindowMemory.ColumnKey` na `ColumnDefinition` zapamiętuje szerokość kolumny po przeciągnięciu `GridSplittera` (lewy panel głównego okna). Nowe okno musi używać `Style="{StaticResource WindowBase}"`.
- **Czat i narzędzia MCP:** `ChatViewModel` + `ToolsViewModel` jako klient narzędzi MCP (`McpToolHost`, konfiguracja w `McpConfig`). Osobno `McpAppServer` (lokalny serwer MCP) wystawia sterowanie aplikacją przez `IAppControl` / `AppControlTools`, implementowane przez `MainViewModel.AppControl`.
- **Przebudowa promptu przez AI** (`IAiProvider.EnhancePromptAsync` -> `OpenAiCompat.EnhanceAsync`): prompt ma dwie osobne części, `system` (konfiguracja generowania: jak wykonać) i `concept` (oczekiwany wynik: co pokazać). Model odpowiada JSON-em o stałej strukturze `{system, concept, changes}`; OpenAI i OpenRouter dostają `response_format` (z ponowieniem bez niego, gdy endpoint go odrzuci), UberLLM nie, bo API odrzuca nieznane klucze. Poprzednie przebudowy (`PromptRevision`, ostatnie 6) są dołączane jako kontekst rozmowy; historia żyje w `PromptEdit.History` i w `MainViewModel` osobno dla zakładek Generowanie i Edycja.
- **Zestawy (presety)** to pliki JSON w katalogu użytkownika (`PresetStore`, rodzaj `generate` albo `edit`). Edytor promptu (`PromptEditorWindow`) dostaje listę zestawów i delegat zapisu jako parametry (nie zna `PresetStore`). Okno zapisu zestawu proponuje nazwę i opis przez AI (`PresetSaveViewModel`). Edytor promptu ma też "Opisz obraz (AI)" (delegat `describeImages` z `IDialogService.ShowPromptEditor`; `MainViewModel.DescribeImagesAsync` wysyła obrazy zakładki albo wskazane pliki do modelu tekstowego z obsługą obrazów).
- Motywy i style (własny szablon ComboBox, wspólne `DataTemplate` modeli) są w `App.xaml`.

## Testy

Projekt `ImageStudio.Tests` testuje ViewModele na tym samym kontenerze co aplikacja: `TestApp.Create()` składa `AddImageStudioCore()` z atrapami (`FakeProvider`, `FakeDialogs`, `FakeThemeService`, `FakeProviderFactory`) i magazynami w pamięci (`Memory*Store`), a `app.Vm` / `app.Get<T>()` zwracają usługi (bez UI i sieci). Konkretny magazyn lub atrapę podmienia się w `TestApp.Create(services => ...)`. Testy z oknami WPF idą przez `WpfHost.Run`. Testy ustawiają `IMAGESTUDIO_DATA_DIR` na katalog tymczasowy (`TestEnvironment.cs`), więc nie dotykają danych użytkownika; ta zmienna nadpisuje `AppPaths.UserDataDir`. Logika w code-behind okien WPF nie jest pokryta, dlatego warto ją trzymać w ViewModelach.
